# dsh-mnemon 0.5.53

- 是否 Cordis 插件 / 入口 / 宿主 inject / provide / 客户端：是，而且是**一组**插件。`cordis.patch.yml` 插入一个 loader 组条目 `mnemon-bundle` (`dsh-mnemon/bundle` = `lib/bundle.js`，`static inject = ["loader"]`，用 loader 的 `group` builtin 再装下面十几个子条目：`dsh-mnemon` 本体 + 4 个 source + 5 个 strategy + 9 个 provider 包)。本体 `lib/index.js`：inject = `tools, settings, commands, agents, subagents`，provide = `["mnemonMemory"]` (`lib/index.js:20077-20085` ✔)。另有 `lib/starter.js` (provide `mnemonStarterReady`) 与 `lib/core.js` (`dsh-mnemon-core`，也 provide `mnemonMemory`，`lib/core.js:4`)，patch 不加载后两者。客户端 `lib/client.js`，inject = `slots, sessions, workspaces, uiSession, connection, locale, layout` (`lib/client.js:30335` ✔)。`bin/repair-legacy-session.mjs` 是独立 CLI，不在本审计范围。本文只审本体、bundle 与 starter；子包 (source/strategy/provider) 是独立 npm 包，未审。
- 一句话功能：可组合的"记忆视图"运行时：提供 `mnemonMemory` 让 source/strategy 子插件贡献内容，注册记忆工具、命令、system prompt 段落、每个 agent 上的生命周期钩子、子代理复盘、Git 自动备份；还管理自身子插件的启停与安装。

**最高层**：不在模型内。`internal/config` 钩子越过模型边界；而且它本质上是编排者 (bundle 组改 loader 树、替换包解析、启停/安装自家子插件)，需要的是编排者义务。单看本体的登记纪律很好 (R1 ✓，可选依赖多用 `ctx.inject`)。
**升级路径**：(1) 去掉 `internal/config` 钩子，把配置校验交给 settings 服务的 `validate` (已有 `hostSettings.register(..., { validate })`)；(2) 把 bundle/starter/插件管理与安装拆成单独的编排者插件，本体只做组件；(3) 未注入的 `loader`/`profileContext`/`credentials`/`workspaceRegistry` 等改成 `ctx.inject` 子 fiber 或显式可选依赖。做完 (1)-(3) 本体可到第 1 层；per-agent 效应改由模型的"交集生命周期"构造承载、启动期迁移挪到运行期后可到第 2 层；第 3 层受设置迁移等状态相关逆所限。

**复核 (2026-11-24)**：`owner.entry.parent.unlink(sibling)` (`lib/bundle.js:57`) 用的 `EntryGroup.unlink` 只从父组的配置数组删掉这一项，不 dispose fiber (deepseek-harness `vendor/loader/src/config/group.ts:31`)；mnemon 只对 `disabled: true` 的重复策略行这样做 (`bundle.js:15-24`)，把它们移进自己的组。这是配置层面的条目移动，不涉及运行中的 fiber。
