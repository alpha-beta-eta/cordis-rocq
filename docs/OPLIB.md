# 贡献模型:受限的操作库(设计草案)

目标:给插件一套**只能用它来碰共享状态**的操作,使恢复精确性与合流所需的服务假设随构造成立,
不再逐个服务证明。

本文只做设计,不含证明。第 7 节列出要证的定理与落地顺序。

## 1. 为什么不自由组合

按状态不相交的组合(按键分开、并排放置、服务的和)本来就是安全的:不同部分上的操作互不相干。
麻烦在**同一份状态上能有哪些操作**。服务假设中的撤销独立与可交换是两两的条件,
每往一份状态上加一种操作,就要和已有的每一种操作重新检查一遍:

- 多重集上的"放入"加上"读个数",就不再可交换;
- 独占登记(`Registry.Register`)加上读同名条目(`Lookup`),就不再独立
  (`Registry.register_lookup_same_not_indep`);
- 有序总线上的登记加上派发,也不再独立(`EventBus.on_emit_not_indep`)。

所以同一份状态上的操作集合没法随构造组合。本方案从源头限制它:**所有服务只有同一种形状,
插件只有两个操作**,组合只发生在没有证明义务的地方。

## 2. 服务的形状

一个服务的状态由两部分组成:

| 部分 | 谁写 | 何时写 | 插件可做的事 |
|---|---|---|---|
| 冻结部分 F | 提供者 | 只在 `Provide` 时给出,之后不变 | 读 |
| 贡献多重集 C | 任何能访问这个服务的 fiber,包括提供者 | 加载时(以及运行期反应中) | 放入自己的贡献 |

状态的等价 ≃:F 相等,C 作为多重集相等(列表的置换)。

插件只有两个操作:

| 操作 | 结果 | 逆 | 会失败? |
|---|---|---|---|
| `Read` | F | 恒等 | 从不 |
| `Put c` | 无 | 撤回一个 c | 从不 |

服务对外的**含义**由一个纯函数给出:

```
view : F × Multiset C → R
```

例如"当前有哪些工具"、"一个事件按什么顺序派发给谁"、"生效的配置是什么"。读 view 的是**宿主**
(派发事件、调用工具、渲染界面),不是插件的启动程序。view 不是操作,所以**没有证明义务**:
它定义在多重集上,自然与贡献的先后无关。

## 3. 组合发生在哪里

只有两处,都是自由的:

1. **贡献类型 C。** 和类型表示几类贡献,`K × V` 表示按键分开,带上优先级 P 表示需要顺序。
2. **view。** 任意纯函数,可以复合、并排、按键投影。

服务之间的组合(把各个服务合成演算要求的单一服务 Σ)仍用已证的 `Compose.Sum`。

## 4. 由构造保证的性质

| 性质 | 理由 |
|---|---|
| 带见证、尊重 ≃ | `Put c` 的逆撤回一个 c;在置换意义下这是精确的逆(`Listeners.listeners_well_behaved`) |
| 逆与状态无关(UI) | 逆只取决于 c |
| 与令牌无关(TI) | 操作不读令牌,也不返回令牌 |
| 可交换 | 多重集上的放入可交换;`Read` 读的 F 不会变,与一切可交换 |
| 之后可达状态上的撤销独立(RA) | 同 `Listeners.listeners_revert_after`;`Read` 的逆是恒等 |
| 不会因别人而失败 | 两个操作都从不失败 |
| 启动程序读不到别人的写 | 唯一的读是 `Read`,读的是常量 F |
| 不存在时间顺序 | 所有顺序都由 view 从数据(优先级)算出 |

因此相遇关系 G 可以取**全部**操作对:任意两个 fiber 在同一个服务上做什么都可以。
插件义务只剩演算原有的那几条(访问的键在 d ∪ p 中、provide 的键在 p 中),不需要再检查
"不同插件不得用同一个名字"之类的条件。

这几条中,`Put` 的部分就是 `Services/Listeners.v` 已证的 `listeners_hyps`。新增的只有常量 F 与 `Read`。

## 5. 已有接口与概念的对应

| 已有的东西 | 贡献模型中的形式 |
|---|---|
| 计数器、引用计数 | C = ℤ,view 求和 |
| `tools.register(name, tool)` | C = Name × P × Tool;view 对每个名字取优先级最高的,并列出冲突 |
| `webServer.register(route)` | C = Route × P × Handler,同上 |
| `ctx.on(event, cb)` | C = Event × P × Cb;view 按优先级(再按 Cb 上的全序)排序后派发 |
| `slots.inject(slot, c)` | C = Slot × P × Component,view 按优先级排序 |
| `tools.restrict(agent, deny)` | C = Agent × Rule;view 取每个 agent 所有规则的并 |
| `ctx.set` / 覆盖写配置 | C = P × Value,view 取优先级最高者 |
| 提供者的配置,依赖者来读 | F |
| 单独撤销某次登记 | 把这次 `Put` 放进一个子 fiber(`O-React` 或 `Spawn`),再 `dispose` 它;不需要句柄 |

旧的服务例子都成为特例:`Listeners` 是 F 为空、C = Cb 的情形;`Registry` 改为按优先级取胜者的 view,
不再有登记失败。

## 6. 代价

1. **启动程序不能根据共享状态做分支。** `Put` 没有结果,`Read` 读的是常量。程序退化成:读提供者的配置,
   做出一组贡献,spawn 一些子 fiber。原型中 `alias` 那种"先查 `ls`,有就起别名"的写法不再能表达。
   可以表达的替代:把别名做成一个贡献,由 view 在 `ls` 存在时才让它生效。
   这正是本方案的意图:依赖时机的读取是合流失败的根源(审计结论 2)。
2. **重名不再在登记时报错。** 冲突由 view 呈现,宿主决定怎么处理(拒绝调用、警告、取胜者)。
3. **提供者不能在运行期改 F。** 提供者的可变状态也只能以贡献的形式放进 C。
4. **可选依赖要换一种表达。** 审计中常见的"有这个服务就用,没有就算了"不能靠启动时读取实现。
   候选做法:由 view 决定贡献是否生效;或者作为编排层的选择(装不同的组件)。见第 8 节。

## 7. 要做的事

**Rocq:**

1. **恢复精确性改由 RA 推出。** `Recovery.recovery_exact` 与 `Runtime.effect_exact` 现在要求的
   `Hind` 是在**所有**状态上成立的撤销独立。按值撤回不满足它:在不含 c 的状态上,撤回 c 会撤掉别人刚放进去的 c。
   但逆只会在放入 c 之后的状态上执行,所以 RA 应当就够了。这是唯一需要改动已有定理的地方。
   - 备选:按令牌撤回(无序的 `EventBus`,已有 `reg_revert_indep`,满足完整的撤销独立),
     代价是状态带令牌,TI 不成立,合流要改成在令牌重命名意义下成立。倾向前者:改的是证明中的一个假设,
     而不是结论的形式。
2. `Lib/Contrib.v`:服务 `Contrib F C`(状态、≃、`Read` 与 `Put`);证明 `ConfHyps (Contrib F C) (fun _ _ => True)`,
   复用 `Listeners.v` 的引理。
3. 把 `Listeners` 重新得到为 `Contrib unit Cb`;`Registry` 换成 `Contrib unit (Name × P × V)` 加取胜者的 view,
   旧的 `Registry.v` 与 `RegistryConf.v` 保留,作为"不受限操作需要额外条件"的对照。
4. 陈述 view 的性质:两个 ≃ 的状态 view 相同。这样合流与恢复精确性的结论(状态在 ≃ 下相同)
   直接推出宿主看到的含义相同。

**Racket(`cordis.rkt`):** 把 `register`/`lookup`/`on` 换成 `Read` 与 `Put`,加上几个 view;
随机调度测试改为比较 view 的值。可以先于 Rocq 做,用来尽早找反例。

## 8. 待定问题

1. **可选依赖。** 用 view 让贡献有条件地生效,还是交给编排层?前者把逻辑推给了宿主,
   后者要求编排者知道组件之间的关系。
2. **运行期的读。** 运行期反应(`O-React`)是否也只能 `Read` 与 `Put`?反应本来就不在合流定理内,
   可以放宽;但放宽后,反应读到的 view 取决于此刻装了哪些插件,恢复精确性仍成立,确定性则不再保证。
3. **view 的复杂度。** 冲突处理、优先级、条件生效都推给了 view。view 没有证明义务,但会成为新的 bug 所在,
   是否需要一个小的 view 组合子库(按键分组、取最大、并、排序)?
4. **外部世界。** 文件、凭据、配置文件不在服务里(审计结论 3)。本方案不覆盖它们:恢复精确性只对上下文陈述。
