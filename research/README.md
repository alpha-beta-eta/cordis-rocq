# 调研:Cordis 演算与 PL 技术的结合点

计划见 [PLAN.md](PLAN.md)。七个方向各一份报告,每份都有领域概览、对照表(注明精确对应、近似对应或仅形似)、
差异、候选课题和核对过的参考文献。

Rust 版 Cordis 的调研单独放在 [rust/](rust/README.md),包括语言机制、插件形态、保证手段三部分。

| 报告 | 一句话结论 |
|---|---|
| [reversibility.md](reversibility.md) 可逆计算与补偿 | 守卫 `¬held` 蕴含因果安全,但比它强:它连与依赖者无因果关系的效应也冻结了,所以不满足细粒度的因果活性。`recovery_exact` 可以读成"因果等价推出共终"(按 ≃),`RevertIndep` 是 Square Property 的两个实例;Loop Lemma 对应的是 `Witnessed`,不是 `recovery_exact` 本身。 |
| [effects-coeffects.md](effects-coeffects.md) 效应与余效应 | `Prog` 就是操作签名上的自由单子,`Bridge.denote` 和 EDSL 的各个解释都是处理器。与效应文献的区别在于:撤销是精确的,余效应的满足是动态的(`provider_outlives`、`held`),用户不能写处理器。审计中的猴补丁、`globalThis` 等,用效应的语言说就是环境权限和能力逃逸。 |
| [session-types.md](session-types.md) 会话类型 | 生命周期骨架(获取、使用、释放)像共享会话,交互内容不像:服务操作没有协议,提供者也不参与。对应最紧的是 Jacobs 与 Balzer 2023 年的高阶锁:唯一的拥有者引用,拥有者等全部客户放下引用之后才回收(对应 `wf_bind`、`withdraw_waits`)。fiber 的四态不适合做类型状态。 |
| [components-dsu.md](components-dsu.md) 动态组件与 DSU | `quiet` 与 Kramer–Magee 的 quiescence 只是名字相近,真正对应 quiescence 的是 `¬held`,而且要求更强。OSGi DS 的 static 策略就是 target 驱动的重载,默认的 reluctant 策略会破坏合流。核心演算卸载时没有状态可迁移,要做 DSU 式的状态迁移,得先引入持久状态。合流在这些文献里基本没有对应物。 |
| [incremental.md](incremental.md) 增量计算与协调 | target 驱动的收敛加合流,就是以静态组装为期望状态的 ESR(Anvil, OSDI 2024),而且对每个调度都成立,不需要公平性。服务状态共享且可变,所以一般做不到"提前截断"。 |
| [concurrency.md](concurrency.md) 结构化并发与监督 | `wf_parent` 加 `parent_waits_child` 就是"子任务不逃出作用域"的不变量。它和结构化并发有三点不同:子 fiber 失败不传给父 fiber,相当于 SupervisorJob;生命期还沿依赖边嵌套,构成一个 DAG;依赖者自动重启,相当于按依赖关系做的 rest_for_one。落地(差异 h)不等于 `mask`。 |
| [verification.md](verification.md) 验证与测试 | lockstep 模型测试适合测**运行时**,不适合测插件:插件是不透明的 TS,所以 checker 现有的自身比较判据要保留。合流定理保证无失败时落定状态唯一,因此抽取出的 `step` 在"落定"这个粒度上可以直接当 oracle。证明 Cordis 精化演算有四档路线,Iris 一档没有现成地基。 |

## 总体结论

1. **演算处在几个领域的交点上,但哪一个领域都没有把它整个覆盖。** 每个方向都找到了精确的局部对应:
   - 自由单子与处理器;
   - 高阶锁的拥有者/客户纪律;
   - 结构化并发的作用域不变量;
   - 可逆计算的 Square Property;
   - ESR。

   但下面三样东西,任何一个领域都没有同时具备:
   - 共享可变服务上的精确撤销;
   - 动态满足的余效应;
   - 合流,也就是"任意调度的终态与静态组装一致"。

   这正是对外表述时可以主张的贡献。

2. **合流是最独特的结果。** DSU 和组件模型的文献按计划执行重配置,Nix 靠构造保证结果唯一,Kubernetes 由用户显式写出期望状态。演算里没有显式的期望状态,合流定理正好用来定义它。

3. **我原先对会话类型的判断偏乐观。** manifest sharing 能给共享服务一个类型上的定位,但给不了撤销和交换方面的元理论。对演算更有用的是会话类型文献里两种证明技术:
   - 按秩证明无死锁;
   - 线性地持有句柄。

   给服务操作加协议这条路,两份报告都不建议走。

4. **几个方向在同一个结构上相遇。** 依赖边与父子边上的"区间嵌套"至少出现了四次:
   - 可逆计算课题 2 的嵌套引理;
   - 会话类型课题 A 的等待关系;
   - 结构化并发课题 C1 的 `dag_scoped`;
   - 会话类型课题 D 的归因链。

   这说明值得先把等待关系与嵌套抽成一个公共文件,后面几个课题都建在它上面。

## 课题排序

按三条标准排序:与现有成果的贴合度、预期收益、工作量。
课题号指向对应报告中的编号,下文提到的 `waits_above` 等名字都是报告提议的新引理,仓库里还没有。

| # | 课题 | 来源 | 产出 | 工作量 |
|---|---|---|---|---|

### 第三梯队:大,或者研究性质

- `recovery_exact` 放进 Lanese–Phillips–Ulidowski 的公理框架(可逆 1)。收益在于理论定位,不产生新结论。
- 局部回卷,只重做受影响的后缀(增量 B)。要放宽 `unload_waits`,合流能否保住目前只是推测。
- 持久状态与状态迁移(组件 C2)。合流对持久部分一般不成立。
- 两段式运行时对演算的模拟(结构化并发 C3)。
- Iris 精化证明(验证 T6);用连通图方法重证无死锁(会话 E)。

### 不建议做

- 给服务操作加会话协议。
- 把四态生命周期做成类型状态。
- DS dynamic 式的就地重绑(组件 C5)。报告预计结论多半是否定的。

## 可靠性说明

- **参考文献。** 各报告的参考文献都经检索核对过。完全未核实的有几条,如 Korth 等的 VLDB 1990、quickcheck-state-machine;另有几条只核实了部分字段,如作者名或卷号。这些在各报告中都已逐条标出。
- **转述依据。** 少数条目的内容转述只依据摘要或二手材料,文中也已注明。
- **定理名。** 报告里被当作已有定理引用的 Rocq 名字,都在仓库中检索确认过存在。候选课题里出现的新名字(如 `waits_above`、`blame_chain`、`sup_agree`)是提议,仓库里还没有。
- **未查证的工程事实。** 有几项报告没有查证,例如 QuickChick 是否支持 Rocq 9.1,以及 dsh 是否真的需要 `Try`/补偿结构,开工前需要先确认。
